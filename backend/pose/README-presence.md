# 平安看护（摄像头看得见老人、且没摔倒，才算平安）

## 这个功能做什么

摄像头开着、画面里能看见老人、并且老人没摔倒，就认为老人平安。

两种情况提示家属看一眼：

- 看不见老人超过设定时长 → `out_of_view`
- 老人摔倒了 → `fallen`

另有一项可选的 `still`（画面内长时间无动作），默认阈值放到 30 分钟，可关。

**刻意做小的范围**：不做房间识别，不做场景分类，不做跌倒之外的异常判断。
判定只用一个现成的姿态模型（yolov8n-pose），不引入第二个模型，不改后端接口。

## 四个状态

| 状态 | 含义 | 是否平安 | 优先级 |
|---|---|---|---|
| `in_view` | 画面内能看到老人，且未摔倒 | **平安** | 0 |
| `still` | 人在画面内但长时间无动作 | 需留意 | 1 |
| `out_of_view` | 连续看不到人超过阈值 | 需留意 | 2 |
| `fallen` | 画面内但判定为摔倒 | 需留意 | **3（最高）** |

**优先级的意义**：同一帧可能同时满足多个条件（例如摔倒后人仍在画面内，
`in_view` 和 `fallen` 都成立）。判定按优先级取最高的那个，
所以 **摔倒永远不会被 `in_view` 覆盖掉**，不会出现「人躺着却报平安」。

## 上报策略（重要）

只在 **「平安 → 需留意」** 和 **「需留意 → 平安」** 这两个时刻各上报一次，
中间持续期间不重复上报。家属端看到的是状态变化点，不是每秒一条观测。

**摔倒额外多发一条**：摔倒时除了 `kind=activity` 的看护状态记录，
还会补发一条 `kind=fall`，走 `rules.py` 产生 critical 告警，
通知子女与社区。两条一起发是因为：

- `activity` 让家属在健康页看到「检测到老人摔倒」这条状态
- `fall` 才是真正触发告警链路、通知到人的那条

只发 `activity` 的话，`rules.py` 对 `activity` 不产生任何事件，**没人会被通知到**。

## 怎么跑

```bash
# 跑一段视频，只打印判定，不写后端（默认带摔倒识别）
backend/pose/.venv/Scripts/python.exe -X utf8 -m backend.pose.presence_run \
    --video 你的视频.mp4 --missing-grace 5 --still-seconds 30

# 接本机摄像头并上报到后端
backend/pose/.venv/Scripts/python.exe -X utf8 -m backend.pose.presence_run \
    --camera 0 --inject \
    --elder-id <老人ID> --password <登录密码>

# 关掉摔倒识别，只做纯在画看护
backend/pose/.venv/Scripts/python.exe -X utf8 -m backend.pose.presence_run \
    --video 你的视频.mp4 --no-fall

# 跑自动化测试
backend/pose/.venv/Scripts/python.exe -X utf8 -m backend.pose.test_presence
```

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--missing-grace` | 60 | 连续多少秒看不到人算「离画」 |
| `--still-seconds` | 1800 | 画面内多久无动作算「长时间不动」，设 0 关闭 |
| `--no-fall` | 关闭 | 关掉摔倒识别，只做纯在画看护 |
| `--stride` | 5 | 每 N 帧推理一次。**开启摔倒识别时会被强制改成 1** |

**关于 `--stride`**：摔倒落地只是几帧的事，跳帧会直接漏掉坠落瞬间。
所以 `PresenceRunner` 在开启摔倒识别时会把 `frame_stride` 强制设为 1 并打印提示。
平安看护本身不需要高帧率，纯在画检测时跳帧开销约为跌倒检测的 1/5。

## 阈值为什么这么取

三个阈值都不是照抄默认值，而是从实测数据里定出来的：

- **`missing_grace_seconds = 60`**：老人转身、被家具或门框挡住一两秒是常态，
  阈值太小会不停误报。60 秒足够容忍正常遮挡与短暂离开。
- **`still_seconds = 1800`**（30 分钟）：老人午睡、静坐看报都会长时间不动，
  阈值太短会变成噪音。设 0 可以完全关掉这项判定。
- **`fall_hold_seconds = 120`**：摔倒检测是单帧触发的，而「人在画面内」是逐帧成立的。
  如果不做保持，摔倒后下一帧就会因为人还在画面里被判回平安。
  保持 120 秒，让摔倒状态"钉住"一段时间，家属来得及看到。
- **质量门槛**见下一节，这是本功能最关键的参数。

## 最容易踩的坑之一：静态背景被误检成人形

**现象**：只按「模型有没有检出人形」判断老人在不在，老人明明走出画面了，
系统仍然认为他在，`out_of_view` 永远判不出来。

**原因**：yolov8n-pose 会把桌椅、门框、光影误检成人形，而且框的置信度不低。

**实测数据**（URFD 素材，640×240，yolov8n-pose）：

| | 框置信度 | 关键点平均置信度 | 框面积占比 |
|---|---|---|---|
| 真人帧 | 0.86 – 0.88 | **0.91 – 0.95** | 0.030 – 0.044 |
| 静态背景误检 | 0.67 – 0.72 | **0.50 – 0.51** | 0.030 |

框置信度和面积两项挨得很近，**只有关键点平均置信度差了近一倍**。

**解法**：加三道质量门槛，三项全过才算「确实有人」。
判定正确性主要由关键点平均置信度保证，另两项做兜底。

```python
min_box_conf       = 0.50   # 框置信度
min_kpt_mean_conf  = 0.70   # 关键点平均置信度（主判据）
min_box_area_ratio = 0.004  # 框面积占比
```

`presence_run.py::_pick_primary` 里逐个候选套门槛，
未通过的帧会记录 `below_quality_threshold` 并给出实测数值，便于排查是不是
真人被误挡了。

## 最容易踩的坑之二：同一套质量门槛会把摔倒的人挡掉

这是把摔倒识别并进平安看护时踩到的坑，比上一个更隐蔽。

**现象**：单独跑跌倒检测时 `fall-01` 在第 109 帧就触发了；
并进平安看护后 `[摔倒]` 一次都没打印过。

**排查**：逐帧 trace 发现关键的那几帧（f=105 / 109 / 115 / 120）
`present=False`，也就是说，**人正在摔倒落地的那几帧，被判定成「画面内没有有效人体」**。

**原因**：人一旦倒地、姿态被打散、被遮挡，关键点平均置信度会掉到 0.70 以下，
正好卡在上一节为防背景误检设的那道门槛下面。
**同一套门槛，一边防误报，一边把真摔倒的人挡了。**

**解法**：两个判定各用各的取人策略，**互不共用**。

```python
def _pick_primary(result, cfg):
    """平安看护取人：套质量门槛，宁可漏检不可误报。"""
    # 三项全过才算「确实有人」

def _pick_for_fall(result, cfg):
    """摔倒检测取人：只按面积取最大，不套质量门槛，宁可误报不可漏检。"""
    # 不套门槛 —— 摔倒时关键点置信度必然下降
```

这个取舍是对称的：

| | 取向 | 理由 |
|---|---|---|
| 平安看护 | 宁可漏检不可误报 | 背景误检成人会让离画判定失效 |
| 摔倒检测 | 宁可误报不可漏检 | 漏掉一次真摔倒的代价远高于一次误报 |

两处取人都拿**同一帧、同一次模型输出**，只是筛选规则不同，不额外跑一次推理。

## 关于上报的 kind 与坐标

上报用 `kind=activity`，`value` 形如：

```json
{
  "state": "out_of_view",
  "label": "老人不在画面内",
  "safe": false,
  "detail": {"missing_seconds": 2.2, "grace_seconds": 60.0}
}
```

**为什么用 activity 而不是新加 kind**：后端 `ObservationCreate.kind` 是 `Literal`
枚举，加 kind 要改后端；而 `activity` 在 `rules.py` 里不产生任何告警事件，
语义上也确实是「状态观测」而非「异常」。实测确认 `activity` 事件数为 0。
摔倒场景则由 `fall` 走正常告警链路，不需要为它加新 kind。

**关于 location**：后端 `_validate_observation_input` 要求 `location` 一旦出现
就必须含 `latitude` / `longitude` 且为合法数值。当前没有上报 location，
`value` 里也不含坐标，不伪造定位。若将来要带上房间名，
需要先与后端确认 location 的字段约定。

## 已知边界

- **多人场景**只取画面里面积最大的那个人，未做身份区分。
  老人在画面里但被其他人挡住时会误判。
- **阈值是演示参数**，正式投用前须按实际机位重新标定
  （`missing_grace_seconds` 尤其要按摄像头视野与实际居家动线调整）。
- **单目姿态估计对机位角度敏感**：URFD 的 cam1 机位下检出率仅 40%
  （cam0 为 63%），因为该角度下人体跌倒时躯干几何读不出「横卧」。
  真实部署前必须让人在实际机位下实际跌倒一次做覆盖测试。
- **「横卧」与「躺下休息」难区分**：剩余误报均属此类。
  居家场景中老人本来就会在床上躺下，这是比公开数据集更难的问题。
- **URFD 不代表家用场景**：手持/固定近景、片段 2–7 秒、跌倒后迅速起身，
  与居家固定广角机位的画面分布差异很大。指标只能说明「链路可用、无退化」，
  **不能直接外推为家用准确率**。
- **不是医疗或专业看护结论**。本判定只表示「摄像头拍不拍得到人、拍到的姿态是否正常」，
  不代表健康状态。
- 依赖 `yolov8n-pose`，**AGPL-3.0 许可**；URFD 素材为学术用途。
  对外分发前均须处理许可问题。
