## 1. 背景与范围

需求来自「演示视频」：希望演示**对着电脑说粤语，通通被唤醒**。

项目当前实现（见主文档第 10 节）：唤醒由前端
[WakeWordControl.vue](../../web/src/components/WakeWordControl.vue) 在首页显式开启后持续调用
浏览器的 `SpeechRecognition`，识别结果经 [wake.ts](../../web/src/lib/wake.ts) 去标点后查唤醒词
`你好通通`，命中则把余下文本交给指令助手。

**因此唤醒完全依赖浏览器自带的语音识别服务**，不经过本项目后端。本文要回答的问题是：

1. 能否用「AI 生成的音频」自动驱动这条链路，从而录制可复现的演示视频？
2. 粤语（`zh-HK`）在这条链路上能做到什么程度？

范围不包括：方言识别服务（`/speech`）的接入，那是另一条链路，见第 5 节与第 7 节第 4 条。

## 2. 结论摘要

| 方案 | 结果 | 关键证据 |
|---|---|---|
| 假麦克风 `--use-file-for-fake-audio-capture` 注入音频 | ❌ 不可用 | 三轮测试均返回**空字符串**，非网络错误 |
| 真实麦克风 + 外放（原始音量） | ⚠️ 勉强，内容错误 | 普通话识别成 `对啊`；粤语几乎全空 |
| 真实麦克风 + 外放（**音频放大 5 倍 + 系统音量调高**） | ✅ **普通话成功** | `你好通通今天天气怎么样`，置信度 **0.90** |
| 真实麦克风 + 外放（同上，粤语） | ❌ 内容完全不对 | 粤语被识别成 `把整个调给删掉吗`，置信度 0.83 |

**一句话**：普通话语音唤醒在正确音量下**可以跑通**；粤语唤醒在当前链路下**不可用**，失败点不在收音、不在网络、不在登录态，而在识别模型对合成粤语音频的识别准确率。

## 3. 测试环境

| 项 | 值 |
|---|---|
| 系统 / 机器 | Windows，ASUS TUF Gaming F15（内置 Realtek 麦克风阵列与扬声器） |
| 浏览器 | 系统 Chrome（`C:/Program Files/Google/Chrome/Application/chrome.exe`），由 Playwright 驱动 |
| 页面 | `http://127.0.0.1:8000`（预览模式，`web/dist` 由后端托管），`isSecureContext = true` |
| 识别服务可达性 | **直连 Google 不可达（HTTP 000）**；经本机代理 `http://127.0.0.1:7897` 可达（HTTP 200）。脚本已显式设置 `--proxy-server` 并放行 `127.0.0.1` |
| 音频来源 | edge-tts 合成（粤语 `zh-HK-HiuMaanNeural` / 普通话 `zh-CN-XiaoxiaoNeural`），ffmpeg 转 16kHz 单声道 WAV |

## 4. 实测过程与证据

### 4.1 基础链路

`probe_browser.cjs` 确认：页面可打开，`hasSpeechRecognition = true`，`isSecureContext = true`。
即 API 层具备条件。

### 4.2 假麦克风方案（失败）

用 `--use-fake-device-for-media-stream` + `--use-file-for-fake-audio-capture=<wav>`
把音频当作麦克风输入，三种组合结果一致：

| 组合 | 日志 | 结果 |
|---|---|---|
| headless + 粤语 `zh-HK` | `logs/probe_speech_h.log` | `onsoundstart` → `onspeechstart` → `result[F]:[""]` |
| headless + 普通话 `zh-CN` | `logs/probe_speech_cmn.log` | 同上，空结果 |
| 有窗口 + 普通话 | `logs/probe_speech_headed.log` | 同上，空结果 |

**判读**：`onspeechstart` 触发说明音频确实被系统感知到；返回结果是**空字符串而非
`error:network` / `error:service-not-allowed`**，说明识别请求本身成功到达了服务。
所以假麦克风的音频**只喂进了 `getUserMedia`，没有进入 `SpeechRecognition` 内部的音频通路**。

结论：这条自动化路径不可用，与粤语无关。

### 4.3 收音质量验证

`probe_mic_level.cjs` 用 `AnalyserNode` 测 RMS：

| 约束 | 静默基线 `avg` | 外放时 `avg` | 结论 |
|---|---|---|---|
| 默认（AEC / 降噪 / AGC 全开） | 0.0122 | **0.0453** | 拾音正常，约 3.7 倍提升 |
| 关闭 AEC / 降噪 / AGC | 0.0103 | 0.0114 | 信号弱，但说明不是「完全没声音」 |

**判读**：外放的声音确实能被麦克风拾到，**问题不在收音**。日志：
`logs/probe_mic_level.log`。

### 4.4 真实麦克风 + 外放（登录后）

`probe_login_yue.cjs` 先登录老人屏再测（确认登录态不影响识别），结果：

| 语言 | 识别结果 |
|---|---|
| 粤语 `zh-HK` | `interim: 不` → 多个 `FINAL: ""`（几乎全空） |
| 普通话 `zh-CN` | `FINAL: 对啊（c=0.91）`、`interim: 老师` |

**判读**：能出中文、且带 0.91 的置信度，说明**识别链路是通的**；但内容是错的
（原始音频为「你好通通，今天天气怎么样」→ 识别成「对啊」），属于典型的
"听得到有声音、但听不清内容"。日志：`logs/pl4.out`。

### 4.5 放大音频后的关键突破

把同一音频用 ffmpeg 放大后再外放：

```bash
ffmpeg -i cmn_wake.wav -af "volume=5.0,alimiter=limit=0.95" cmn_wake_loud.wav
```

同时在脚本里用 `SendKeys([char]175)` 发送 20 次音量加键提高系统音量。结果（普通话）：

```
4.1s [interim] "你"
4.3s [interim] "你好"
4.5s [interim] "你好通通"
5.0s [interim] "你好通通"                置信度 0.90
5.8s [interim] "你好通通今天天气怎么"
5.8s [interim] "你好通通今天天气怎么样"
6.4s [interim] "你好通通今天天气怎么样"    置信度 0.90
```

**完整识别，唤醒词与指令都对。** 日志：`logs/pf1.out`。

**判读**：之前判定「外放拾音不可用」是**音量不足导致的误判**，应修正。
唤醒词 `你好通通` 与后续指令均被正确识别，`wake.ts` 的匹配逻辑可以正常工作。

### 4.6 粤语单独复测

同一条件下单独测粤语（`zh-HK` + `yue_wake_loud.wav`）：

```
1.5s [interim] "把"
1.9s [interim] "把整个"
3.0s [interim] "把整个调给删掉吗"
3.6s [interim] "把整个调给删掉吗"          置信度 0.90
11.5s [FINAL] "把整个调给删掉吗"          置信度 0.83
```

**判读**：与原始音频「你好通通，今日天气点样」**毫无关系**。`zh-HK` 模型能出结果，
但对合成粤语音频的识别准确率不可用。日志：`logs/pf_yue.out`。

可能原因（未验证，见第 7 节）：
① `zh-HK` 模型对 edge-tts 合成音的适配差；② 合成音是逐字粤读，与模型期待的口语表达不匹配；
③ 粤语音节经「外放 + 空气 + 内置麦克风」后失真放大。

## 5. 方言 TTS 合成实测（另一条链路）

用 `check_dialect_tts.py` 直接打 `POST /api/elders/{id}/speech/synthesize`，
文本统一为「你好，我是通通。今天天气不错。」：

| `dialect` | 状态 | 字节数 | 判定 |
|---|---|---|---|
| `zh-CN` | 200 | 24624 | `zh-CN-XiaoxiaoNeural` |
| `yue-HK` | 200 | **31104** | `zh-HK-HiuMaanNeural`，**真粤语音色** |
| `northeast` | 200 | **28224** | `zh-CN-liaoning-XiaobeiNeural`，**真东北音色** |
| `sichuan` | 200 | **24624** | 与 `zh-CN` **逐字节相同** → 回落普通话 |

**判读**：`edge_tts._cache_key` 含音色名。四川话与普通话同为 24624 字节，说明命中的是同一音色缓存，
与代码中 `DIALECT_FALLBACK["sichuan"] = "zh-CN"` 一致，**四川话暂无免费川味音色得到实证**。

同时确认：**播报侧（TTS）零配置可用**（edge-tts 走公开接口，不需要 Key），
粤语与东北话都有真音色。这与「识别侧未配置」是两个独立状态。

## 6. 结论

1. **浏览器唤醒依赖外部识别服务**：本机直连不可达，必须走代理。这一点在任何演示环境都要预先确认，否则表现为"叫了没反应"。
2. **自动化注入音频不可行**：`--use-file-for-fake-audio-capture` 喂不进 `SpeechRecognition`。想要无人值守录制唤醒，
   只能靠「外放 + 真实麦克风」，而这条路径依赖音量与环境噪声，**不适合作为稳定演示手段**。
3. **普通话唤醒可跑通**：在音频放大 + 系统音量足够的前提下，识别出 `你好通通今天天气怎么样`（置信度 0.90）。
4. **粤语唤醒不可用**：`zh-HK` 把粤语合成音识别成完全无关内容。**粤语方向不应按"调参就能成"来规划**。
5. **需要区分三件事**，它们在项目里状态不同：
   - 浏览器唤醒（前端 `SpeechRecognition`）：普通话可行、粤语不可行；
   - 方言识别服务（后端 `/speech`）：**未配置**（`QWEN_API_KEY` 为空），前端会直接拦下并提示改用文字入口；
   - 方言播报（后端 `/speech/synthesize`）：**已可用**，粤语/东北话有真音色，四川话回落普通话。

## 7. 待确认问题

1. **普通话唤醒的可重复性**：目前只有单次成功记录（置信度 0.90）。需要连跑多次统计成功率，
   才能判断它能否作为演示或验收手段，还是仅"偶尔能成"。
2. **粤语是否有其他可行路径**：换粤语音色（如 `zh-HK-WanLungNeural`）、改用更口语化的粤语句式、
   或改用真实人声粤语录音，是否能让 `zh-HK` 正确识别？当前未验证。
3. **是否引入虚拟声卡**：安装 VB-Cable 之类把音频直接灌入录音设备，可绕开「外放 + 空气 + 内置麦克风」
   的失真路径。代价是需要管理员权限装驱动，且属于改动本机环境，需评估。
4. **方言识别服务是否接入**：若要让「老人用粤语对通通下指令」真正可用，必须配置 `QWEN_API_KEY`
   （归一化为普通话书面语）或讯飞（需单独开通方言条目）。这是与唤醒无关的另一条链路。
