# 老友 — 吊装机位跌倒检出：标定结论与可靠性边界

> **文档梗概**：应「把实录的吊装机位跌倒检出」这一需求，做了一轮机位标定搜索。**结论是可以检出，但不建议按此上线** —— 该配置的检出依赖姿态估计抖动造成的单帧伪影，在丢帧下会失效，且本机位没有任何负样本可供验证误报率。文中给出可直接使用的标定参数与使用方式，同时如实列出不可靠之处。

## 1. 需求

素材 B（房间吊装高机位，720×1280，7.97s）是团队**实录的真实跌倒**：
站立行走 → 3.1–3.5s 屈膝前扑 → 3.5s 起躺在地板上不起。基线（62°/5 帧）**漏报**。

需求：**让这段能被检出为跌倒。** 不是把阈值随便调低，而是要说明"调到多少、代价是什么、能不能信"。

## 2. 结论摘要

| 问题 | 答案 |
|---|---|
| 能不能检出？ | ✅ **能**。`torso_angle_threshold` 降到 52°（确认帧仍 5），`t=3.60s` 正常告警 |
| 代价是什么？ | URFD 全量精确 **0.724→0.636**、F1 **0.712→0.667**，误报 8→12（每个场景数） |
| 这个检出可信吗？ | ❌ **不可信**。三条硬证据见第 4 节 |
| 关键原因 | 素材 B 的"坠落信号"是姿态估计抖动造成的单帧尖峰，不是平滑下落的真实测量 |
| 建议 | **demo 可用，生产慎用**。真正解决需要本机位的标注数据（正+负样本） |

## 3. 标定搜索结果

搜索维度：`torso_angle_threshold` × `lying_confirm_frames` × `immobility_seconds`。
评估：URFD 全量（100 分卷 / 70 唯一场景，从缓存重放）+ 素材 A/B 必须检出。

**能检出素材 B 的配置，按 URFD F1 排序：**

| 角度阈值 | 确认帧 | B 触发 | URFD 召回 | URFD 精确 | URFD F1 | URFD FP | F1 代价 |
|---|---|---|---|---|---|---|---|
| 62°（现状） | 5 | ✗ | 0.700 | 0.724 | **0.712** | 8 | — |
| 58° | 4 | ✓ 3.87s | 0.733 | 0.647 | 0.688 | 12 | −0.024 |
| 55° | 5 | ✓ 3.67s | 0.700 | 0.656 | 0.677 | 11 | −0.035 |
| **52°（推荐）** | **5** | **✓ 3.60s** | 0.700 | 0.636 | 0.667 | 12 | **−0.045** |
| 50° | 5 | ✓ 3.57s | 0.700 | 0.600 | 0.646 | 14 | −0.066 |

**为什么推荐 52° 而不是 F1 更高的 58°：** 素材 B 躺下平台（idx 104–117）的躯干角为
42.1~63.1°、中位 56.5°、**最小 56.0°**。阈值放在 58° 落进了平台内部，
要靠平台末端恰好 4 帧连续达标才成立，余量太小；52° 在平台下沿留出约 4° 余量。

**素材 B 躺下平台实测**（stride=1）：17 帧落在 3.4–4.0s，角度 42.1~63.1°，中位 56.5°。
4.0s 之后角度回落到 25~45°（见第 4 节）。

## 4. 可靠性边界（三条硬证据）

### 4.1 证据一：坠落信号是姿态估计抖动，不是真实下落

素材 B 的鼻部纵坐标（`nose_y`）在 3.0s 前后的逐帧增量：

```
t=2.933  nose_y=0.299   (+0.007)
t=2.967  nose_y=0.306   (+0.007)
t=3.000  nose_y=0.336   (+0.030)  ← 突跳
t=3.033  nose_y=0.338   (+0.002)  ← 几乎不动
t=3.067  nose_y=0.346   (+0.008)
t=3.100  nose_y=0.347   (+0.001)
t=3.133  nose_y=0.378   (+0.031)  ← 又突跳
```

**+0.030 / +0.002 交替出现**，是姿态模型在头部关键点上反复"跳位"的典型形态，
不是连续的下落运动。检测器把这种抖动当成了"坠落速度 0.897/0.906 画面高/秒"。

物理上也讲得通：**吊装高机位下，人倒向地面主要是在画面"深度方向"上位移**，
在图像纵坐标上只产生很小、且阶梯式的变化，本来就不该出现 0.9 画面高/秒的"下落速度"。

### 4.2 证据二：丢帧后全部失效 —— 0 组鲁棒配置

用 `frame_stride`（每 N 帧推理一次）模拟丢帧。要求素材 B 在 stride=1/2/3 下**都**检出，
搜索了 5 档角度 × 3 档确认帧 × 3 档下降阈值 × 2 档角速度阈值 = **90 组**：

```
鲁棒配置共 0 组
```

原因正是 4.1：隔帧采样会采到那些"+0.002"的帧，把测得的下降速度稀释掉。

| 采样 | 实测下降速度峰值 | 是否越过 0.8 阈值 |
|---|---|---|
| 全帧（stride=1） | **0.906** | ✅ |
| 隔帧（stride=2） | 0.555 | ❌ |
| 3 帧取 1（stride=3） | 0.44 | ❌ |

隔帧时状态机会走到「横卧姿态确认中 5/5」→「**横卧但无坠落证据（疑似躺下/坐下）**」，
卡在坠落证据这一支。

> 真实性提示：真实部署中降帧率、丢包、CPU 抢占都会等效于 stride≥2。
> **一个只在全帧率下成立的检出，不能算检出。**

### 4.3 证据三：`vertical_ratio` 判据被证伪

原本设想用 `vertical_ratio`（躯干竖直跨度）作为**与躺向无关**的横卧判据
（素材 B 躺下时它从 0.22 塌到 0.08，约 2.7×）。实测其区分度：

角度落在 35~62°（灰区）时的 `vr` 分布：

| 分组 | 帧数 | p10 | p50 | p90 |
|---|---|---|---|---|
| URFD 真跌倒（fall-*） | 657 | 0.048 | **0.105** | 0.159 |
| URFD 日常（adl-*） | 612 | 0.031 | **0.105** | 0.174 |
| B-房间吊装（躺下后） | 75 | 0.082 | 0.097 | 0.107 |

**真跌倒与日常动作的 `vr` 中位数完全相同（0.105）**，帧数也相当。
逐档扫描（要求 `vr ≤ X` 才算横卧）显示两组同比缩放，没有任何一档能把 adl 单独筛掉。

**结论：`vr` 在现有形态下没有额外区分度，不能用作横卧判据。**
这条设想被实测否决，不要据此改代码。

## 5. 一条抗丢帧的替代思路

「持续低位时长」（`vr ≤ 0.12` 连续保持多久）天然抗丢帧 —— 少采几帧不影响还算得出 2 秒。
实测：

| | 最长持续低位 |
|---|---|
| B-房间吊装 stride=1 / 2 / 3 | **2.30s / 2.27s / 2.30s** ✅ 三档一致 |
| URFD 真跌倒（30 场景） | p50=0.52s，p90=2.11s |
| URFD 日常（40 场景） | p50=0.47s，p90=1.84s，max=3.53s |

按「持续低位 ≥ X 秒」筛选：

| X | URFD 跌倒命中 | URFD 日常命中 | B（三档） |
|---|---|---|---|
| 1.0s | 5 / 30 | 13 / 40 | ✓✓✓ |
| 2.0s | 4 / 30 | **3 / 40** | ✓✓✓ |
| 2.5s | 1 / 30 | 3 / 40 | ✗✗✗ |

**判读：抗丢帧这一点成立，但区分度不够干净**（X=2.0s 时日常仍有 3/40 命中，
且这 3 个大概率就是 URFD 里「在床上躺下」的场景）。
若作为独立判据需配合「从直立转为低位」的转移条件，**本次未实现、未验证**。

## 6. 落地建议

### 6.1 Demo / 演示可用（今天就生效）

**演示视频**：`scripts/diagnostics/pose-fall-verify/second/demo-compare.mp4`
（13.1s / 720×758 / 30fps）。同一段实录左右并排：左「基线 62°」全程漏报、
右「标定 52°」3.60s 告警。关键区间（2.9~4.2s）慢放 3 倍，
每个面板带角度标尺（同时标出 52° 与 62° 两条阈值），结尾附结果对照与注意事项。

已给 `backend/pose/run.py` 增加机位标定覆盖项，不必改源码：

```bash
backend/pose/.venv/Scripts/python.exe -X utf8 -m backend.pose.run \
  --video <吊装机位视频> --torso-angle 52 --confirm-frames 5 \
  --json out.json
```

实测（素材 B）：**告警 1 次，首次 3.60s**。`--json` 会把本次生效的整套阈值一并写入，
便于事后核对用的是哪套标定。

新增参数：`--torso-angle`、`--confirm-frames`、`--descent-speed`、
`--angular-velocity`、`--exit-fall`。

重录演示视频：

```bash
backend/pose/.venv/Scripts/python.exe -X utf8 tmp/fall-verify2/demo.py
```

### 6.2 生产环境不要直接用

理由是第 4 节的三条证据，加上最根本的一条：
**本机位没有任何负样本。** 素材 B 是唯一一段本机位素材，且是正样本。
「调低阈值会在本机位产生多少误报」根本无从测量 —— 而调低阈值正是提高误报的标准做法。

### 6.3 要真正解决，需要做的事

1. **采集本机位的标注数据**：至少 20 段真实跌倒 + 40 段日常动作
   （走动、坐下、弯腰、地上捡东西、躺沙发），且必须覆盖**正常帧率**。
2. **在数据上重新设计特征**。当前两个特征在高机位下都不适用：
   - 图像纵坐标下降速度 → 高机位下位移落在"深度方向"，信号极弱（4.1 佐证）
   - 躯干投影角 → 依赖人体躺向的方位角，不是"是否躺下"的稳定度量
   方向建议：地面平面单应变换后的**离地高度**，或**躯干图像长度 / 肩宽**之比
   （后者对躺向免疫，但需实测确认是否与侧视机位冲突）。
3. **重新评估**：把本机位数据与 URFD 合并评估，避免"调一个机位、坏一个机位"。

### 6.4 不要过度表述

- **不能说「跌倒识别已支持居家吊装机位」。** 目前只有 1 段正样本、0 段负样本。
- **不能引用 52° 这个数字对外宣称准确率。** 它只保证素材 B 这一段能报警。
- 素材 B 能报警这件事本身，**依赖的是姿态估计伪影**（4.1），不是算法能力提升。

## 7. 复现方式

```bash
cd D:/实验室项目/LaoYou_ChuangXin_Agent
P=backend/pose/.venv/Scripts/python.exe
D=scripts/diagnostics/pose-fall-verify/second

# 端到端：用标定参数跑素材 B（应告警 1 次，首次 3.60s）
$P -X utf8 -m backend.pose.run --video $D/input.mp4 \
   --torso-angle 52 --confirm-frames 5 --json tmp/calib-run.json

# 机位标定搜索（必须检出 B，看 URFD 代价）
$P -X utf8 tmp/fall-verify2/calibrate_overhead.py

# 鲁棒性：候选配置在丢帧下能否检出（结论：0 组）
$P -X utf8 tmp/fall-verify2/robustness.py
$P -X utf8 tmp/fall-verify2/robust_search.py

# 为什么隔帧失效（逐帧判定，定位到"无坠落证据"）
$P -X utf8 tmp/fall-verify2/diag_stride.py

# vr 判据是否可用（结论：无区分度）
$P -X utf8 tmp/fall-verify2/vr_analysis.py

# 持续低位判据可行性（抗丢帧，但区分度不干净）
$P -X utf8 tmp/fall-verify2/sustained_feasibility.py
```

> 脚本内的相对导入基于仓库根目录，需在根目录执行。
> 特征缓存：`tmp/fall-verify2/urfd-features.pkl`（URFD 全量）、
> `tmp/fall-verify2/b-strides.pkl`（素材 B 三种采样率）。
