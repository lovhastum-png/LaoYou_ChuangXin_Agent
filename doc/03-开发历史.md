**三类文字浮层是可分别开关的**（2026-10-06）。`build.py` 的 pass2 不再把字幕写死，`--no-sub`（旁白字幕）/ `--no-tag`（章节标签）/ `--no-head`（跌倒段三支的标题条）可任意组合，全关时连 `ass` 滤镜都不挂、只走一个 `null` 统一标签。成片文件名随之加后缀（如 `老友-功能演示-无字幕.mp4`），**只要关掉任意一项就不会覆盖已交付的原片**：

```bash
backend/.venv/Scripts/python.exe -X utf8 tmp/rec/build.py --final --no-sub
```

判定"真的去掉了"不能只看文件生成成功——滤镜链少挂一次可能整段静默无字幕，也可能把视频链写断。`tmp/rec/verify_nosub.py` 给的是可核对的两组证据：两片同一时刻、同一条带的差异像素比，以及纵向拼接的对比图。实测结果是**干净得超出预期**：除了旁白字幕那一条带（平均差异 18.01%，最高 30.64%），章节标签带、标题条带、片头对照带与有字幕版**逐字节一致（0.00%）**。两片是同一批 norm 素材、同参数 libx264 编码，x264 对相同输入是确定性的，所以"一个像素都没动"本身就成了很强的证据，而不是"看起来差不多"。

### 8.2 修掉的真实缺陷：注入观测表单必崩

- **位置**：`web/src/pages/FamilyWorkspace.vue` 的 `injectObservation()`。
- **现象**：家属端「注入观测」填好观测类型与数值后点「写入模拟观测」，页面提示"观测注入失败，请稍后重试。"，**浏览器网络面板里没有任何请求发出**。
- **根因**：Vue 3 对 `<input type="number">` 的 `v-model` 会自动把值转成 number（`@vue/runtime-dom` 的 `vModelText` 中 `el.type === "number"` 走 `looseToNumber`）。而代码写的是 `injection.value.value.trim()`，类型已经是数字，`.trim` 不存在 → 抛 `TypeError`，被 `catch` 收下后落到通用失败文案。`duration_minutes`、`latitude`、`longitude` 三个同样是数字输入框，同样的写法。
- **修复**：加一个 `text(v) = v == null ? '' : String(v)`，所有取值先转字符串再 `trim()`。
- **验证**：`tmp/rec/probe/live-14-inject.png` 显示修复后表单出现绿色提示"已写入 heart_rate 观测，产生 1 个事件。"；`web` 侧 `vue-tsc --noEmit` 0 error；重建 `web/dist` 后 `GET /` 返回的入口为 `assets/index-43Q6sK2q.js`（已确认后端在托管新产物）。

### 9.2 修掉的真实缺陷 ①：预览启动器从不读 `runtime/local.env`

- **现象**：文档一直让用户"把 `QWEN_API_KEY` 填进 `runtime/local.env`"，但填了也没用——桌面端方言识别始终不可用。
- **根因**：这份文件只有两条读取路径——`database.py`（建库连接串）和 `scripts/start.ps1`（PostgreSQL 路径）。而本机跑不起来 PostgreSQL，日常走的是 `scripts/preview.py`（双击 `启动老友-预览.cmd`），**它一个字都不读这个文件**。于是"配置入口"实际上不存在。
- **修复**：新增 `scripts/localenv.py` 作为唯一解析器，`preview.py` 启动前读取并覆盖到子进程环境（与 `start.ps1` 的 `SetEnvironmentVariable` 语义一致，环境变量优先于文件）。启动横幅把"语音识别/语音播报当前是否可用"以及"配置来自哪个文件"直接打出来——省得用户只能靠猜。
- **验证**：临时在 `runtime/local.env` 追加一行伪造的 `QWEN_API_KEY`，**另起一个 8011 实例**，其 `/api/capabilities` 变成 `speech.configured: true`，而 8000 那个仍是 `false`；`POST /speech` 会带着可读的错误信息从上游返回（402/401 一类的鉴权失败），说明请求确实走到了通义千问那一层。验完立刻删除伪造 key，`local.env` 恢复为全注释状态。

### 9.3 修掉的真实缺陷 ②③：界面文案与事实相反

这两条都是"补上去的诚实说明本身说了假话"，恰好背离了这三项工作的目的。

**② 试听播报时界面一个字都不显示**

- **现象**：播报卡片上点「🔊 播放」——有声音，但界面上看不到任何状态，更看不到用的是哪个音色。
- **根因**：播报状态（`正在合成语音…`／`正在播放…`／`音色：xxx`／停止按钮）被写在助手结果块 `assistantResult?.let { ... }` **内部**。而试听只调用 `speakReply(broadcast.text)`，不产生助手结果 → 整段渲染不到。这恰好把"能区分方言播报真的生效还是回落成普通话"的唯一证据藏掉了。
- **修复**：把播报状态整段移到助手结果块之外，成为独立的一段；助手结果块里只留「🔊 重念一遍」（它依赖 `assistantResult.reply`，必须留在里面）。
- **验证**：插桩用例 `broadcastPlaybackUsesServerVoiceWhenAvailable` 现在能等到 `音色：zh-CN-XiaoxiaoNeural`，截图见 `tmp/voice-shots/voice-04-playback.png`。

**③ 首页宣称"电脑端语音不可用"，可它正用着服务端音色**

- **现象**：同一屏上一边显示「音色：`zh-CN-XiaoxiaoNeural`」（服务端 edge-tts 合成成功），一边写「电脑端的语音合成不可用，播报会用手机自带语音，只有普通话」。
- **根因**：`GET /api/capabilities` **只在切到「设置」页时**才请求（`AppShell` 里 `AppTab.SETTINGS -> onLoadCapabilities()`）。首页拿到的 `capabilities` 永远是 `null`，而 `speechRouteNote`／`broadcastRouteNote` 对 `null` 取的是最悲观分支。于是首页的两条说明全部失真；「设置」页因为自己拉了一次，反而是对的——这也是为什么自检直觉会判断错方向。
- **修复**：登录后（`LaunchedEffect(api?.token)`）立刻拉一次能力清单，设置页保留原刷新。首页与设置页的结论从此由同一份数据驱动。
- **验证**：修复后首页播报说明变为「播报用电脑端合成，普通话女声」，与实测音色一致（`tmp/voice-shots/voice-04-playback.png`）。并给插桩用例补了一条**一致性断言**：既然已经用服务端音色念出来了，卡片上就不得再出现「电脑端的语音合成不可用」。
