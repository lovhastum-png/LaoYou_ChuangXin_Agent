## 0. 摘要

| # | 结论 | 依据强度 |
|---|---|---|
| 1 | 老年人视觉衰退的核心是**对比敏感度下降**，而非单纯"看不清小字"。同一字号下，提高亮度对比比放大字号收益更大。 | 强（多组纵向研究） |
| 2 | 老年人**蓝-黄通道**辨色能力衰退最明显，实证易混淆色对为：**黄/白、蓝/绿、深蓝/黑、紫/暗红**。蓝色不适合作为唯一信息载体。 | 强（色觉实验） |

| 4 | 现有界面 **67 处文字小于 16px**、**对比度普遍只达 AA(4.5:1) 未达适老 7:1**、**分隔线与开关轨道仅 1.3~1.7:1（硬性不达标）**。 | 实测（本机渲染） |
| 5 | 缺少**字号可调**能力。工信部规范对适老版是强制要求"应可对字型大小进行调整"。 | 强制性标准 |
| 6 | 颜色只解决"**看得清**"。另外三个失败原因——**够不着**（手够不到）、**认不出**（字再大也读错）、**读不懂**（不识字）——需要布局、字体、图案三个**正交维度**分别解决，且**不可捆绑**（见 §14）。 | 本方案判断 + 实测 |

> 结论 6 对应的实施在 **§14**：布局（含左手优先 / 图形优先两档）、字体族、装饰图案共三个维度，与配色 / 明暗 / 字号 / 密度叠加后**共七个维度任意组合**。

## 1. 为什么是现在做

### 1.1 用户基数

中国互联网络信息中心（CNNIC）第 56 次《中国互联网络发展状况统计报告》（2025 年 6 月）：

- 全国网民 11.23 亿，互联网普及率 79.7%
- **60 岁及以上银发网民 1.61 亿，老年群体互联网普及率仅 52.0%**

这意味着**近半数老年人仍处于"不会用、不敢用、不愿用"状态**（国务院发展研究中心王伟进语）。老友的目标用户正落在这个区间。

### 1.2 政策环境（已从倡导转为法律义务）

| 文件 | 性质 | 与本项目的关系 |
|---|---|---|
| 《中华人民共和国无障碍环境建设法》（2023-09-01 施行） | **法律** | 明确要求互联网服务提供者保障无障碍 |
| 工信部《移动互联网应用（APP）适老化通用设计规范》（2021-04） | **部门规范** | 给出字号、行距、对比度、组件尺寸的**具体数值** |
| 工信部《促进数字技术适老化高质量发展工作方案》 | 政策 | 适老化改造的推进要求 |

对本项目的意义：老友定位是"面向独居老人的适老化总控屏"，**适老化不是加分项，是产品成立的前提**。目前若被评审或用户质询"哪里适老了"，我们没有可引用的量化依据——这份文档补上这一环。

## 2. 依据一：感官层——视力与色彩感知

### 2.1 关键机制：对比敏感度（CSF）下降

很多人把老年人视觉问题理解为"看不清小字"，这只对了一半。更准确的说法是：

> **老年人对"低对比度"的分辨能力系统性下降，且下降在中高空间频率（细节、细线、小字）上最严重。**

实测数据：

- 20 岁与 70 岁观察者在 8 cycles/degree 处的对比敏感度差异为 **0.2–0.57 log units，平均约 0.3 log units**（Elliott 1987/1990/2009；Kline et al. 1983；Owsley et al. 1983，经 Owsley 综述汇总）。
- 日本 NILS-LSA 纵向研究（40–79 岁社区人群，n 较大）：**即使矫正视力达到 1.0，70–79 岁组中仍有 21.1% 的人在高空间频率（18 cpd）处对比敏感度为零**。
- 结论原话："仅靠视力检查无法评估老年人群的视觉功能"——**视力表正常 ≠ 界面看得清**。

机制分解（多因素叠加）：

| 因素 | 后果 |
|---|---|
| 瞳孔缩小（miosis，约 60 岁后趋于稳定） | 进光量下降 |
| 晶状体密度增加、黄化 | 进光量下降 + 短波长（蓝）被吸收 |
| 眼内散射增加 | 对比度被"雾化" |
| 视网膜照度下降 | 低亮度条件下额外恶化 |

综合效果：**进入老年眼睛的光量下降 28–43%，相当于常年戴一副墨镜看屏幕。**

**→ 设计约束**：不能假设"我们的对比度达到 4.5:1 就够了"。4.5:1 是**年轻眼睛的最低阈值**，不是适老目标。

### 2.2 晶状体黄化与色觉偏移

晶状体随年龄变厚变黄，**选择性吸收短波长（蓝紫）光**。由此产生两类问题：

**（1）色相感知偏移**

老年人视网膜实际接收到的光谱里蓝光减少，画面整体偏黄。主观"黄视感"在 **75 岁以上人群中显著**。

**（2）实证易混淆色对**

一项针对 80 岁以上被试的色觉判断实验 + 黄化镜片模拟研究给出的易混淆组合是：

| 易混淆色对 | 风险等级 | 老友界面是否涉及 |
|---|---|---|
| **黄 / 白** | 高 | 需检查（天气图标、警示底色） |
| **蓝 / 绿** | 高 | **涉及**（主色为蓝，历史主色为绿，改造期存在混用风险） |
| **深蓝 / 黑** | 高 | **涉及**（`--brand-deep #0F3D73` 与 `--ink #111C2E` 均为深色） |
| **紫 / 暗红** | 中 | 不涉及 |

同一研究还指出：**红-橙-黄等长波长色因能穿透黄化晶状体，保留最好**。这是"暖色更适合老年人"这一常见说法的来源。

**（3）蓝锥细胞（S-cone）数量最少**

人眼三种锥细胞中蓝锥数量最少，蓝通道本身最脆弱。**色对比敏感度研究（Hardy et al. 2005）显示：老年观察者在所有空间频率、两种色觉通道上均表现出更低的敏感度**，且控制眼介质密度差异后差异仍存在，说明光学术与神经因素共同作用。

### 2.3 由此推出的设计约束

| 约束 | 具体数值 | 来源 |
|---|---|---|
| 正文亮度对比 | **≥ 7:1**（不要停在 4.5:1） | WCAG 1.4.6 AAA + 适老实践建议 |
| 关键内容对比 | **≥ 10.5:1** | 适老实践建议 |
| 非文本元素对比（边框、图形、控件边界） | **≥ 3:1** | WCAG 1.4.11 AA + 工信部 1.3 |
| 颜色不得作为唯一手段 | 必须配图标/文字/形状 | WCAG 1.4.1 + 工信部 1.4 |
| 字号 | 适老版主要文字 **≥ 18dp**；正文不低于 16px | 工信部 1.1 / NN/g |
| 行间距 | **≥ 1.3 倍**；段间距 ≥ 行距 × 1.3（WCAG 更严：行高 ≥1.5、段距 ≥2×字号） | 工信部 1.2 / WCAG 1.4.12 |

## 3. 依据二：运动层——精细动作控制

### 3.1 手部控制衰退

- **年龄相关的运动控制退化从 50 岁后开始**，影响握力、精细动作、视-动协调。
- **特发性震颤（essential tremor）患病率：40 岁以下 4%，65 岁以上 14%。**
- 触摸精度**每十年下降约 15%**（40 岁后）。
- 老年人触摸偏移实测典型值为 **0.8–2.1mm**（这正是各类"触摸校正算法"要解决的量级）。
- 触屏研究：**44×44 的目标，65+ 用户错误率约 19%；放大到 56×56 降至 8%；64×64 降至 5%**（34 名 65–82 岁被试的实践测试报告）。
- 人体测量：平均指尖接触面积 **10–14mm（约 28–40 CSS px）**，拇指 12–20mm。
- Harte et al. (2017) 针对老年用户的建议更激进：按钮面积 **≥ 200mm²（约 89×89dp）**。

### 3.2 老友的输入场景特殊性

老友的 WebUI 是**电脑总控屏**，主要用鼠标。而鼠标对老年人的难度**高于**触屏：

> NN/g 观察：一位 80 岁老人经常用**两只手**操作鼠标——在精确点击目标和移动光标两件事上都有困难。鼠标点击目标建议**对角 ≥ 11mm**（比触屏的 9.6mm 更宽）。

**→ 设计约束**：

| 项目 | 下限 | 目标值 |
|---|---|---|
| 触屏目标（Android APP） | 48×48dp（Material） | **60×60dp**（工信部适老版） |
| 鼠标目标（Web 总控） | 44×44px | **≥ 48×48px，主要操作用全宽按钮** |
| 相邻目标间距 | ≥ 8px | ≥ 12px |
| 手势 | 避免 ≥ 3 指复杂手势 | 单击优先 |
| 反馈 | 需明确视觉 + 听觉反馈 | 点击后 0.2–0.3s 内可见反馈 |

## 4. 依据三：认知层——注意力、工作记忆与决策

### 4.1 认知负荷理论（Cognitive Load Theory, Sweller 1988）

CLT 把认知负荷分为三类，其中**外在负荷（extraneous load）——由界面呈现方式造成的、与任务无关的负担——对老年用户的影响最大**，因为它直接由设计决定。

CLT 推导出的三条界面原则：

| 效应 | 含义 | 对老友的要求 |
|---|---|---|
| **分裂注意效应** | 相关信息分散在多处会增加负担 | 同一件事的说明与操作放一起，不要让用户在弹窗间跳转 |
| **冗余效应** | 无意义的重复信息反而增加负担 | 不要同时用三种方式说同一句话 |
| **通道效应** | 多通道（视+听）呈现优于单一通道 | 老友已有语音播报，应继续扩大语音覆盖 |

### 4.2 具体能力变化

- **执行功能下降 → 难以过滤无关信息**：页面上的次要元素会实际干扰主要任务，不是"看着乱"而已。
- **工作记忆容量下降 → 易过载**：跨屏幕记住信息很困难（如"刚才那个页面写的什么"）。
- NN/g 实测：老年组**记忆保留率 49%，年轻组 63%**。

### 4.3 量化建议

综合多份研究的推荐值：

| 项目 | 建议值 | 来源 |
|---|---|---|
| 界面层级 | **≤ 3 层** | ACM 数字鸿沟研究 |
| 每层菜单项 | **4–6 项** | 同上 |
| 首页关键功能数 | 平板 ≤ 12，手机 ≤ 6，**尽量无需滚动即见全部** | mHealth 老年人设计研究 |
| 数据输入步骤 | **≤ 3 步** | 多项 mHealth 研究一致 |
| 图标风格 | **具象/拟物优于扁平抽象**（与年轻用户偏好相反） | HCI 老年人设计研究 |
| 术语一致性 | 同一概念全站统一措辞（不要"返回/后退/上一步"混用） | mHealth 综述 |

## 5. 依据四：心理行为层——信心、自责与放弃率

NN/g 两轮跨年代研究（针对 65+ 用户）给出的行为数据，对本项目尤其重要：

| 指标 | 老年人 | 21–55 岁 | 设计含义 |
|---|---|---|---|
| 视觉能力评分 | 82% | 95% | — |
| 灵活性（Dexterity） | **73%** | 95% | 目标要大、间距要足 |
| 记忆保留 | **49%** | 63% | 减少跨屏依赖 |
| 尝试新路径的比例 | 低 | 约 2 倍于老年 | **不要依赖用户"自己探索"** |
| 失败后放弃的概率 | 约 2 倍于年轻人 | — | 错误必须可恢复 |
| 放弃时间 | 比年轻人**早 30 秒** | — | 请求超时不宜过长 |
| 出错时自责比例 | **90%** | 58% | 错误文案不能带指责语气 |
| 使用搜索引擎比例 | 比年轻人**高 51%** | — | 说明界面不可发现性差 |

另有：**45% 的老年人表现出"不愿尝试新事物"的行为**；**中老年用户完成同一任务的效率比年轻用户低 74%**。

**→ 设计约束**：

1. **所有关键功能必须在首屏可见**，不依赖用户滚动或探索。
2. **每个错误都要给出"下一步怎么办"**，而不是只报错；老友现有文案（"找不到这台电脑，请检查服务地址是否填写正确"）方向是对的，应继续。
3. **不要有超时压力**。老友现有的 15s 请求超时是给网络用的，但**面向老人的确认弹窗不应自动消失**。
4. **操作必须可撤销**（工信部附录也有此要求）。

## 6. 专项结论：配色该怎么定

这是本轮最容易做错的一步，单独说清楚。

### 6.1 证据指向

- NN/g 面向老年用户的设计指南中明确列出：**"在重要的互动界面元素上避免使用蓝色。"**
- 蓝/绿、深蓝/黑是实证易混淆色对（见 2.2）。
- 蓝色在白底上的对比度，对老化眼睛感知约 3.5:1（有眼科医生公开引用此量级）。

**看起来结论是"不能用蓝"——但这是过度简化。**

### 6.2 本方案判断：可以继续用蓝，但必须换一种用法

理由：

1. **决定可读性的是亮度对比，不是色相。** 老年人 CSF 下降导致的问题，**可以通过提高亮度对比来补偿**。蓝色之所以"不好"，是因为常见蓝色（如链接蓝 #0066CC）亮度太低。把蓝色加深到 7.5:1 以上，可读性即可回到安全区。

2. **改用暖色主色会引入更严重的问题。** 老友的状态语义已经占用暖色：
   - 橙 `#b25407` = "待提醒 / 需留意"
   - 红 `#b63d28` = "异常 / 挂断 / 错误"

   若主色也变暖色，则**"品牌色"与"警示色"语义重叠**，直接违反"颜色不得作为唯一信息手段"（工信部 1.4）——用户将无法靠颜色判断"这是按钮还是警告"。

3. **大面积高饱和暖色对老年人并不友好。** 红橙黄虽然穿透黄化晶状体最好，但大面积使用会产生眩光感与视觉疲劳；暖色的优势在**小面积强调**（这正是它适合做警示色的原因）。

4. **蓝色作为"低饱和、大面积、非语义"的装饰色是安全的**，危险的只是"蓝色作为唯一语义载体"（蓝色链接、仅靠颜色区分的按钮）。

### 6.3 具体动作

| 动作 | 现状 | 目标 |
|---|---|---|
| 主色亮度对比 | `--brand #1B62B8` 6.02:1 | 加深至 **≥7.5:1**（如 `#16559C` 量级，实施时精确校验） |
| 次要文字对比 | `--muted #5C6875` 5.69:1 | 提高至 **≥7:1** |
| 蓝色语义降级 | 多处"蓝色 = 可点击" | 补**图标 + 边框 + 文字**冗余编码 |
| 深蓝/黑区分 | `--brand-deep` 与 `--ink` 均为深色 | 确保二者不会在同一区域并置比较 |
| 健康页双蓝冲突 | `.health-card-icon.brand` 与 `.blue` 视觉接近 | **必须拉开色相或改用形状区分**（见 7.2） |

> **2026-09-28 补充**：本节结论（"可以用蓝，但要换一种用法"、以及"主色不得占用橙红语义"）在 §13 落地为两条**机制**而非仅设计约定：
> - 主色的亮度由求解器强制解到 7:1 以上，"深浅"不再依赖手工挑色；
> - 六套预设主题的色相**被约束在避开橙红区间**，且用户自定义主色撞上橙/红时会得到提示。

## 7. 现状盘点（实测）

对 `web/src/styles.css` 的静态分析与 WCAG 对比度计算结果如下。

### 7.1 字号分布

| 字号 | 出现次数 | 评价 |
|---|---|---|
| 11px | 2 | ✗ 严重偏小 |
| 12px | 5 | ✗ 严重偏小 |
| 13px | 17 | ✗ 偏小 |
| 14px | 24 | ✗ 偏小 |
| 15px | 26 | ✗ 偏小 |
| 16px 及以上 | 约 70 | ✓ |

**合计 74 处文字小于 16px**（其中 7 处 ≤12px）。对照 NN/g"老年站点至少 12pt(=16px)"与工信部"适老版主要文字 ≥18dp"，当前辅助信息层普遍偏小。

另一方面：大标题与关键数字达到 30–108px（时间显示 101px、品牌名 108px），**这部分做得很好**，说明问题集中在"辅助信息层"而非主干。

### 7.2 关键色对对比度实测

| 色对 | 实测 | 等级 | 是否达标 |
|---|---|---|---|
| 正文 `--ink` on 白 | **17.08:1** | AAA | ✓ |
| 次要强 `--muted-strong` on 白 | 9.36:1 | AAA | ✓ |
| 品牌深 `--brand-deep` on 白 | 10.85:1 | AAA | ✓ |
| 白字 on 品牌深 | 10.85:1 | AAA | ✓ |
| 品牌 `--brand` on 白 | 6.02:1 | AA | △ 需提高 |
| 白字 on 品牌 | 6.02:1 | AA | △ 需提高 |
| 信息蓝 `--blue` on 白 | 6.41:1 | AA | △ 需提高 |
| 红色 `--red` on 白 | 5.70:1 | AA | △ |
| 次要 `--muted` on 白 | 5.69:1 | AA | △ 需提高 |
| 品牌 on 浅底 | 5.28:1 | AA | △ |
| 橙 `--orange` on 白 | 5.04:1 | AA | △ |
| **橙 on 橙浅底** | **4.55:1** | AA | ⚠ **几乎贴线** |
| **分隔线 `--line` on 白** | **1.33:1** | — | ✗ **硬性不达标（需 3:1）** |
| **分隔线强 `--line-strong` on 白** | **1.66:1** | — | ✗ **硬性不达标** |
| **开关轨道 `#C9D2DE` on 白** | **1.53:1** | — | ✗ **硬性不达标** |

**要点**：

- 文本层**全部达到 AA(4.5:1)**，无一失败——基础是好的。
- 但**没有任何一项达到适老建议的 7:1**（除正文与深色标题）。
- **非文本对比出现硬性 FAIL**：分隔线、边框、开关轨道远低于 WCAG 1.4.11 要求的 3:1。开关轨道尤其严重——**用户可能找不到开关在哪**。
- 橙色在浅橙底上 4.55:1 几乎贴线，"待提醒"是老人端首页的关键状态文案，一旦显示器亮度/环境光不利就会读不清。

### 7.3 交互目标尺寸

达标（≥44px）：导航项 70px、图标按钮 44px、主按钮 44px、通话控件 46px、挂断 47px。

**不达标**：

| 元素 | 高度 | 问题 |
|---|---|---|
| `.switch-track`（开关） | 24px | ✗ 关键交互，严重偏小 |
| `.notification-icon` | 30px | ✗ |
| `.call-status-icon` | 40px | △ |
| `.text-button` | 无 min-height（padding 4px 0） | ✗ 实际高度约 22px |
| 表格行内操作按钮 | 依赖 `.icon-button` 44px | ✓ 已修复过 |

**另**：工信部对**适老版界面主要组件要求 ≥60×60dp**，目前 Web 端主按钮为 44px，低于该值。

### 7.4 结构性缺口

| 缺口 | 说明 |
|---|---|
| **无字号调节机制** | 工信部强制要求"应可对字型大小进行调整"，当前字号全部为硬编码 px，用户无法调整 |
| **无高对比模式** | 适老实践普遍建议提供 |
| **字号单位** | 全站 px，不支持随系统字体设置变化（浏览器默认字号调整无效） |
| **状态冗余编码不完整** | 部分状态仅靠颜色（如"已播报"绿色勾 vs "待提醒"橙色）虽有图标，但颜色仍是主要区分手段 |

## 8. 改造方案

### 8.1 视觉层级：重建字号体系

不改布局结构，只调整字号层级。建议目标体系：

| 层级 | 用途 | 当前 | 目标 |
|---|---|---|---|
| 展示级 | 时间、品牌 | 101 / 108px | 保持 |
| H1 | 页面标题 | 31–52px | 保持 |
| H2 | 卡片标题 | 23–29px | **≥ 24px** |
| 主要正文 | 提醒内容、健康建议、按钮 | 15–19px | **≥ 18px** |
| 次要正文 | 说明、副标题 | 13–15px | **≥ 16px** |
| 标注级 | 数据来源、时间戳 | 11–13px | **≥ 14px**（且必须 ≥7:1 对比） |

**风险与对策**：提升次要字号会导致部分卡片变高、表格变宽。因此这一步**必须配合布局微调**（如放宽 `grid-template-columns`、减少同屏信息量），不能只改字号。建议先在老人端首页试点，验证后再推广。

### 8.2 对比度：全站提到适老等级

修改变量表（精确值在实施时用脚本校验）：

| 变量 | 现值 | 目标对比度 | 方向 |
|---|---|---|---|
| `--muted` | `#5C6875` (5.69:1) | ≥7:1 | 加深 |
| `--brand` | `#1B62B8` (6.02:1) | ≥7.5:1 | 加深 |
| `--blue` | `#27648a` (6.41:1) | ≥7:1 | 加深 |
| `--orange` | `#b25407` (5.04:1 / 橙底 4.55:1) | ≥7:1 | 加深 |
| `--red` | `#b63d28` (5.70:1) | ≥7:1 | 加深 |
| `--line` | `#D9E0EA` (1.33:1) | **≥3:1** | 显著加深 |
| `--line-strong` | `#C0CAD8` (1.66:1) | **≥3:1** | 显著加深 |
| 开关轨道 | `#C9D2DE` (1.53:1) | **≥3:1** | 显著加深 |

> 注意：`--line` 与 `--line-strong` 同时用于"卡片边框"和"表格分隔线"。加深到 3:1 后视觉会更"重"，需同步降低边框数量（能用间距表达的就不画线），否则界面会显得割裂。**这是本方案里最容易翻车的一步，建议单独做视觉评审。**

### 8.3 交互目标：全部提到 48px 以上

- 通用下限从 44px → **48×48px**。
- **开关（`.switch-track`）重建**：轨道视觉可保持 24px 高，但**整个 `.switch-field` 需保证 ≥48px 可点击高度**（label 包裹即可，无需改结构）。
- `.text-button` 增加 `min-height: 44px`（视觉不变，用 padding 撑开）。
- 相邻交互元素间距 ≥8px（当前 `.row-actions` 的 `gap: 2px` 需调整）。
- 老人端主要操作按钮（如"打电话""添加提醒"）考虑**放宽到 60px 高**（对齐工信部适老版要求）。

### 8.4 增加"字号档位"（结构性改动）

这是唯一需要动架构的一项，也是工信部的强制要求。

**做法**：CSS 单位从 `px` 迁移到 `rem`，根字号由变量控制。

```css
html { font-size: calc(16px * var(--font-scale, 1)); }
```

原计划提供三档（标准 1.0 / 大 1.15 / 特大 1.3）。**实施时调整为四档**（0.9 / 1.0 / 1.12 / 1.25），原因见 §13.2：档位间距收窄后 1.25 与 1.3 的观感差异不明显，而"小"档是家属端小屏场景实际提出的需求。

**成本**：`styles.css` 中约 120 处 px 字号需换算为 rem（可脚本化）。布局间距建议同步 rem 化，否则放大字号会挤压布局。

**建议**：作为第二阶段，先完成 8.1–8.3（纯数值调整，低风险），验证后再做。

> **已于 2026-09-28 实施完毕**，实际换算 156 处字号声明；间距则**不采用 rem**，改由独立的密度变量驱动（见 §13.2 的取舍说明）。验收数据见 §13.4。

### 8.5 状态冗余编码

对每个依赖颜色的状态，补齐第二种编码：

| 状态 | 现有 | 补齐 |
|---|---|---|
| 已播报 / 待提醒 | 图标 + 颜色 | 加文字标签（部分已有），确保形状不同 |
| 健康数据正常/异常 | `--brand` / `--orange` 圆点 | 圆点改为**不同形状**（实心圆 / 三角） |
| 健康页三种图标卡 | brand蓝 / orange橙 / blue钢蓝 | **两个蓝必须拉开**（改形状边框或显著换色相） |
| 通话状态 | 颜色 | 已有文字，保留 |

### 8.6 认知与内容

- 老人端首页：确认关键功能**无需滚动即见**，控制在 6 项以内。
- 术语统一：全站统一"返回"，不要混用"上一步 / 后退"。
- 错误文案：保留现有的"怎么办"结构（这是正确做法），并检查是否有让用户自责的措辞。
- 确认类弹窗：**不设自动关闭倒计时**。
- 减少跨屏信息依赖：如提醒设置页的说明，直接内联而非跳转。

### 12.2 对比度（全部提升到 WCAG 2.2 SC 1.4.6 增强级 7:1）

| 令牌 | 原值 | 原对比度 | 新值 | 新对比度 |

## 13. 多主题与用户自选外观（2026-09-28）

> §12 交付的是**一套**经过适老校验的配色。本节交付的是**十二套**——六套预设主题 × 明暗两种模式——外加让用户自己给一个主色。核心问题是：**怎么保证"可自选"不等于"可自选到不达标的颜色"。**

### 13.1 范围与四组可调维度

范围：**仅 Web 总控端**。Android 侧未改动（`sp` 单位已天然支持系统级字号缩放，见 §12.7）。

| 维度 | 档位 | 作用对象 |
|---|---|---|
| 配色主题 | 科技蓝 / 黛青 / 松墨绿 / 绛紫 / 靛蓝 / 石墨 + **自定义主色** | 全套色彩令牌 |
| 明暗模式 | 浅色 / 深色 / 跟随系统 | 全套色彩令牌（另解一套） |
| 字号档位 | 小 0.9 / 标准 1.0 / 大 1.12 / **特大 1.25** | `html` 根字号 → 全站 rem（**共 156 处**） |
| 圆角与密度 | 直角 0.3 / 标准 1.0 / 圆润 1.6；紧凑 0.85 / 标准 1.0 / 宽松 1.15 | `--radius-*`；`--sp-*` |

**密度只作用于间距，绝不作用于字号**——否则用户"调密度"会连带把字也调了，两个变量互相污染。字号由 `--font-scale` 单独驱动，圆角由 `--radius-scale` 单独驱动，三者互不干涉。

**未按角色设置默认值**：原方案设想"老人角色默认大字号"，实现时未做（默认一律"标准"）。这是一个已知缺口——目前老人端与家属端默认档位相同。若要补，应在登录后按 `role` 落一次初始偏好（仅首次），而不是在读取偏好时按角色覆盖，否则用户改过的选择会被角色默认值吃掉。

### 13.2 架构：为什么不靠 JS 换肤

```
web/src/styles.css            静态：:root 基础令牌 + 12 个 [data-theme='x'][data-mode='y'] 令牌块
web/src/lib/theme/            运行时：只往 <html> 写 data-* 属性与三个倍率变量，并持久化
web/index.html                内联引导脚本：首帧之前铺好属性与自定义色令牌
```

- **预设主题完全不依赖 JS 渲染**：`[data-theme][data-mode]` 是纯 CSS 选择器，所以不存在"先画一帧默认蓝再跳色"的首屏闪烁——这是把主题放进 CSS 而不是 JS 的唯一理由，也是本方案坚持的做法。
- `styles.css` 是**生成产物**，由 `tmp/apply_theme_system.py` 全量重建，禁止手改；人工维护的样式（外观面板自身）放在 `web/src/styles/appearance.css`，只消费令牌。
- **自定义主色必须靠 JS**，因为它不存在于任何静态块里。对策是把它解算出的令牌一并持久化，内联引导脚本读出来即可在首帧前铺上（见 13.5）。

尺度变量写法：`--sp-N: calc(var(--density) * Npx)`、`--radius-*: calc(var(--radius-scale) * Npx)`、`html { font-size: calc(16px * var(--font-scale)) }`。

> **踩坑记录**：`margin: -7px` 这类负值不能直译成 `-var(--sp-7)`——这是**非法 CSS，浏览器会整条丢弃该声明**，而不是忽略负号。正确写法 `calc(-1 * var(--sp-7))`。本项目 `styles.css` 中原有 2 处（`.notice-bar`、`.call-note`）踩了这个坑，症状是深色模式下顶栏看着不对，改动量却看不见——因为声明根本没生效。

### 13.3 三个关键设计判断

#### （1）品牌色必须拆成**三**个角色，不是两个

| 角色 | 令牌 | 解算基准 |
|---|---|---|
| 前景 | `--brand` / `--brand-deep` | 文字、描边、装饰。**深色模式下要提高亮度**才看得清 |
| 实底 | `--brand-solid` / `--brand-deep-solid` | 实心填充，底下压**不透明**白字（按钮、导航选中项） |
| 面板 | `--brand-panel-from/to/hover` | 品牌渐变面板端点，底下压**半透明**白字 |

**为什么必须拆出第三个**：半透明白 ≠ 白。`--brand-solid` 是按不透明白 7:1 解算的，把 0.83 白的次要文字压上去只剩 **5.96:1**，0.9 白的标题只剩 **6.75:1**——**全部不合格**。这是本轮唯一一处"以为已经达标、实测发现违规"的地方，也是 §12 那套单主题方案遗留的缺口。

修正办法是给面板单独解一组更深的端点（`solve_panel()`，48 步二分，目标：面板最亮端仍能让 0.83 白达到 7:1）。以科技蓝浅色为例，面板渐变由 `#165198 →` 改为 **`#0D2C4F → #154780`**：

| 白字透明度 | 落在旧端点 `#165198` | 落在新端点 `#154780` |
|---|---|---|
| 0.90 白（标题） | 6.75:1 ✗ | **7.94:1** ✓ |
| 0.83 白（次要） | 5.96:1 ✗ | **7.01:1** ✓ |
| 0.72 白（小字） | 4.92:1（≥4.5 即可） | 5.67:1 |
| 0.68 白（小字） | 4.57:1 | 5.26:1 |
| 0.55 白（装饰） | 3.57:1（≥3 即可） | 4.02:1 |

修正后六套主题的 0.9 白一律 **7.94:1**、0.83 白 **7.01–7.05:1**，全部达标。

**校验方法上的要点**：半透明前景**必须先 `over(fg, bg)` 真实合成**（α 混合后取整）再算对比度，直接拿 `rgba(255,255,255,0.83)` 去套公式会得到错误结论。

**附带发现的性质**：品牌渐变面板在六套主题下，**明暗两种模式的端点是同一组值**。这是正确的——面板始终是"深底 + 白字"的独立图层，与页面明暗无关，因此不必也不应跟随时变。

#### （2）嵌套白面不变量（全案风险最高处）

助手面板里嵌着一批**在两种模式下都保持白色**的元素：白色气泡、提案卡、输入框、麦克风按钮。因此它们内部的文字必须**永远使用浅色模式那套深色值**（`--on-brand-surface-ink / -muted / -brand`），**不能跟随全局明暗模式**。

若图省事让它们跟随全局，深色模式下就会变成"浅字压浅底"——白面上出现近乎不可读的文字。这是唯一会让改动"整页报废"的地方，已用截图逐个确认（`tmp/theme-shots/assistant-azure-dark.png` 等）。

#### （3）状态语义恒定

橙（待提醒 / 需留意）与红（异常 / 挂断 / 错误）**只随明暗模式变，不随主题变**。六套预设的色相刻意避开橙红区间。这把 §6.2 的判断从"一条设计理由"升级成"一条机制约束"：

- 用户自定义主色时，若色相落在**橙（30°）或红（8°）附近 24° 内且饱和度 ≥ 0.12**，设置面板直接给出文字提示（已实测：`#b4321e` 相差 0°、`#c2711c` 相差 1° 均触发；冷色 `#2f6f8f` 不触发）。
- 提示不是禁止，是告知——最终仍由用户决定，但不让"主色和警示色长得一样"这件事悄无声息地发生。

### 13.4 验收：三层验证，每层抓上一层抓不到的

| 层 | 脚本 | 结果 |
|---|---|---|
| ① 色板数学 | `tmp/theme_palette.py` | **12 色板 × 46 令牌 = 552 项，0 失败**。每个令牌按**它真实的承载底色**解算（橙字解在橙底上、分隔线解在相邻面板上），不是一律对白底 |
| ② 结构 | `tmp/check_css.py`、`tmp/check_styles_audit.py` | 大括号配平；**0 处未定义 `var()`**、0 处畸形 `var()`、0 个定义未引用的死令牌；12 个主题块键集合完全一致（46 键）；**全站零硬编码色值**，字号全 rem，间距/圆角全部走 `--sp-*` / `--radius-*`——扫描范围含 `styles.css`、`styles/*.css` 及**所有 `.vue` 的 `<style scoped>`** |
| ③ 真浏览器实测 | `tmp/audit_contrast_browser.py` | 逐元素合成祖先背景链后实测。**12 色板 × 2,040 个文字实例，0 失败**，最紧一例 **7.20:1** |

三层各自解决了一个具体盲区：

- ② 之所以要覆盖 `.vue` 的 `<style scoped>`，是因为 `.broadcast-player` 的底色写在了组件内联样式里（`#EDF4FC` / `20px`），生成脚本看不见它——**只有在深色模式下才暴露**，浅色下与页面同色看不出来。
- ③ 之所以需要真浏览器，是因为**渐变写在 `background-image` 里，不是 `backgroundColor`**：只读 `backgroundColor` 的探针会把渐变面板当成透明，从而对"白字压渐变面板"报出 1.05:1 的**假阳性**（18 例）。按 W3C 口径，渐变必须取**对比度最差的那个色标**评估。
- ③ 还抓到了一处②和①都不可能发现的真实违规：主题选择器的**选中态**里，`--muted` 是解在 `--surface` / `--bg` / `--surface-soft` 上的，却实际渲染在 `--brand-soft` 上，实测 6.65–6.77:1（3 例）。修法是把选中态的小字改用 `--brand-deep`。**这类错误只有把元素真的画出来量一遍才发现得了。**

构建侧：`vue-tsc --noEmit` 退出码 0；`vite build` 通过（CSS 67.49 kB / gzip 11.91 kB，JS 215.61 kB）。

### 13.5 自定义主色的实现要点

用户只给一个色相，系统**固定色相与饱和度、只重新解算明度**，用与 `tmp/theme_palette.py` 完全相同的求解器在浏览器里现场反解出整套 46 个令牌。目的：

1. **浅色模式**下主色要承担正文着色，下限 7:1；
2. **深色模式**下同一色相必须变亮才看得清，但变亮之后又压不住按钮上的白字——所以前景角色与实底角色必须分成两组分别求解（即 13.3 的第 1 点）。

面板不让用户凭感觉试：选色时实时显示三个**实测**读数（正文对比度最紧 / 次要文字 / 按钮白字）。以 `#b4321e` 为例，实测 7.88:1 / 7.74:1 / 8.56:1——即使用户选了一个"撞语义"的色相，对比度下限依然守得住。

持久化：`localStorage['laoyou.appearance.v1']`，同时存下自定义主题解算结果，供内联脚本首帧前使用。

> **踩坑记录**：`buildCustomTokens()` 早期版本把 `baseSurfaces(mode, hue, sat)` 的结果直接 `Object.assign` 进令牌表，但该函数返回的是 camelCase 键，导致后续所有 `t['--surface']` 读到 `undefined`，整页崩成白屏（截图只有 19 KB 纯白）。已改为逐键显式映射，并补了 `checkTokenSet()` 自检——令牌集合与预设不一致时直接 `console.error`，不再静默失败。
>
> **踩坑记录**：点「自定义主色」时色板显示 `#165198` 但界面毫无变化——因为 `customPrimary` 仍是 `null`，即"看起来选中了、实际没应用"。已加 `selectCustom()`，点选即提交并显示**解算后**的主色。

## 14. 布局 / 字体 / 图案：三个正交维度（2026-09-29）

> §13 交付的是"可自选颜色"，但颜色只解决**看得清**。老人用不下去还有另外三个原因：**够不着**（手够不到操作区）、**认不出**（字形太像、字再大也读错）、**读不懂**（不识字，文字量再大也没用）。
>
> 本节把这三件事拆成三个**互不捆绑**的可选维度。它们是用户明确提出的需求："每个预设主题的布局和字体也要不一样，而且还要说明为什么要这么布局，比如更加利好左撇子的一版，卡通图案更多，适合不识字老年人的一版"。

### 14.1 为什么不绑进配色主题，而是拆成独立维度

初版设想是"每个主题自带一套布局和字体"，即十二套主题 = 十二套完整外观。**这个方案是错的**，因为这三个需求彼此**方向相反**：

| 组合 | 冲突 |
|---|---|
| 大图标（不识字） × 多卡通图案 | 认知症老人需要**减少**视觉噪声，多图案会加重干扰。若绑在一起，"要大图标"就必须"接受一屏卡通" |
| 大字号 × 左手布局 | 二者独立：右手用户也可能需要大字号，左手用户也可能视力正常 |

所以最终拆成三个独立维度，加在原有的配色 / 明暗 / 字号 / 密度之上，**共七个维度，任意组合**：

| 维度 | 档位 | 属性 | 作用于 |
|---|---|---|---|
| 布局方式 | 标准 / **左手优先** / **图形优先** | `[data-layout]` | 元素**结构**（排列顺序、网格列数） |
| 字体 | 系统默认 / **黑体** / **人文衬线** | `[data-font-family]` | 字体族、字重、行距 |
| 装饰图案 | 简洁 / **丰富** | `[data-motif]` | 卡片角落的装饰纹样 |

三者与配色、字号、密度、明暗**完全正交**：`[data-layout='lefty'][data-font-family='humanist'][data-motif='rich'][data-theme='pine'][data-size='xlarge'][data-mode='dark']` 是一个合法组合，实测可同时生效（见 14.5）。

实现上仍沿用 §13.2 的纯 CSS 路线——全部靠 `<html>` 上的 `data-*` 属性命中，不用 JS 渲染结构。**这一条在布局维度上比配色更关键**：布局变化会改变元素位置，若等 JS 执行完再改，用户会看到"先按标准布局画一次、再跳成左手布局"的内容位移，比换色闪烁更难接受。因此内联引导脚本（`web/index.html`）在首帧前就把三个属性一并写上去。

### 14.2 布局方式之一：左手优先（`lefty`）

**先说清楚这一档解决什么问题**，否则很容易做成"看着不同、用着没用"的假档位。

页面骨架是：左侧 254px 固定导航（`.side-nav`）+ 右侧内容区（`.main-area`）。对左手持握的人，**困难不在导航**——导航本来就在左边，很好按；困难在于**内容区里最高频的操作落在右下角**，左手指过去要横跨整个屏幕，且手腕要往外翻，是个反关节姿势。

四件事：

1. **两个高频操作（通话、摄像头）改为竖排单列并靠左**。为什么是竖排而不是"两栏对调"：两栏无论怎么对调，总有一张卡离左手更远；竖排后两张卡纵向堆叠在左侧同一条竖直线上，左手拇指沿弧线上下移动即可覆盖。
2. **「添加提醒」按钮从卡片右端挪到左端**——它是提醒卡上唯一的可点元素。用 `align-self` + `margin` 实现，**不用 `direction`**，因为这里只需挪一个元素，犯不着为它翻转整张卡的文字方向。
3. **可点元素最小高度抬到 56px**（WCAG 2.5.5 AAA 是 44px）。左手精细操作较少，抬高误触成本是必要的。
4. **内容区收窄并靠左**。实测：内容区宽 1186 → 1080px，右边缘从视口边（1440）回到 1334，网格右内缩从 38px 拉到 322px。

**⚠️ 刻意不做「整页镜像到 RTL」**：中文阅读方向是左起，整页镜像会让日期、数字、标点全跑到错误位置，老人会直接读不出来。**镜像的是操作区，不是阅读方向**——这是这一档最重要的取舍。

**⚠️ 「贴左」指的是内容区内的左对齐，不是屏幕最左**：左侧 254px 是导航栏，内容区只能从它右边开始。若要让操作真正贴屏幕边缘，得把导航也挪走，那会改变全站结构，超出"预设主题"的范围。

| 指标 | 标准 | 左手优先 |
|---|---|---|
| 内容区宽度 | 1186px | **1080px** |
| 内容区右边缘 | 1440（顶到视口边） | **1334** |
| 网格右内缩 | 38px（居中） | **322px**（明显靠左） |
| 底部两卡 | 并排两栏 | **竖排单列** |
| 触碰下限 | 默认 | **56px** |

### 14.3 布局方式之二：图形优先（`pictogram`）

面向**识字很少或不能阅读**的老人（文盲、认知退化、重度低视力）。

**为什么不能用"把字号调到特大"代替？** 因为字号再大，读不懂的字依然读不懂。这一档要换的是**信息编码方式**：把识别负担从"读文字"转移到"认图形"——图形识别是人类更低阶、更抗老化的能力，不依赖读写训练。

四件事：

1. **图标放大到接近卡片的视觉主体**，文字退居辅助位置。
2. **缩短长文**——天气建议之类整句文字折叠为两行（`-webkit-line-clamp`），并加大行距。老人扫视困难，密排文字会被直接跳过。
3. **强化"图标 + 状态色"的编码**：待提醒用橙色、异常用红色，让状态不必读文字即可分辨（状态色口径见 §13.3 第 3 点，此处只做强调，不引入新色）。
4. **增大卡片高度与图标四周留白**——图形识别需要周围有"呼吸区"，紧贴边框的图标反而更难辨认。

实测：图标 svg 43px → **72px（×1.7）**，容器 118px → 148px，卡片高度 226px → 355px，装饰箭头隐藏（它是"往右看"的提示，对不识字用户是无意义符号）。

> **踩坑记录**：第一版只放大了图标容器（`.quick-icon`），实测图标**几乎没变**（118px → 132px，仅 ×1.1）。原因：lucide 图标把尺寸写在 **svg 自身的 `width`/`height` 内联 HTML 属性**上（`:size="43"`），只改容器尺寸不会覆盖它。必须把 CSS 选择器直接打到 `svg` 上（`.quick-card .quick-icon svg { width/height }`）才生效。

### 14.4 字体与装饰图案

**（1）字体为什么独立于字号**——因为"**字大**"和"**字好认**"不是一回事。同样 22px，不同字体的实际辨识度可能差出一倍，关键在于**笔画对比度**和**字形之间的区别度**。

| 档位 | 字体族 | 为什么留这一档 | 代价 |
|---|---|---|---|
| 系统默认 | `system-ui` 等 | 零下载、零布局跳动 | 不受控：Windows 雅黑 / 安卓思源黑体 / macOS 苹方的字面与笔画都不同 |
| **黑体** | 思源黑体 / Noto Sans CJK | 视网膜老化会**先丢失细微笔画的对比**，衬线体的"横细竖粗"在低视力下会让细笔"消失"；均匀笔画在这一步退化中保留更好，远距离更稳 | 字形区别度略低（如「己已巳」），需配大字号 |
| **人文衬线** | 思源宋体 / 宋体 | 对**轻度低视力、仍保有精细辨识能力**的老人，衬线提供的**字形区别度反而更高**——「未末」「天夭」这类近形字在黑体里更易混，衬线靠笔画轻重能分开 | 细笔画在重度低视力下会丢，故配套加大字重（500）与行距，且**不降低最小字号** |

行距随字体族联动：衬线 1.65 / 黑体 1.55 / 系统 1.5。衬线字面小，需要更松的行距才不挤；黑体字面满，行距略紧些以保证信息密度。

**（2）装饰图案为什么独立于布局**——因为"图标优先布局"和"加卡通装饰"是两个**反向**需求：不识字老人要**大图标**（功能性图形，帮助识别），但认知症老人可能被**多余装饰干扰**（装饰性图形，增加噪声）。绑在一起就会出现"为了大图标被迫接受一屏卡通图案"的荒谬组合。所以**功能性图标由 `[data-layout]` 控制，装饰性图案由 `[data-motif]` 控制**。

`motif=rich` 时在卡片角落加一层低对比度同心圆点阵，纯 CSS（`radial-gradient`）实现、**零图片请求**，颜色取自 `--brand` 所以换主题自动跟随：

- 不透明度压到 **0.1**——装饰不能抢正文注意力，也保证它作为背景图形远低于 3:1，不会被误读为可交互元素。
- 图形优先布局下降到 **0.06**：那一档的用户最不需要额外图案，且卡片内容已居中的大图标，角落放图案会破坏对称。
- 深色模式下压到 **0.07**：浅色图案在深底上观感更"亮"，同样的 0.1 在深色背景上更强。

### 14.5 验收：用几何量测，不靠肉眼

布局这东西"看起来不一样"和"真的不一样"是两回事。专门写了 `tmp/shot_layouts.py`，把关键元素的**几何量出来**再断言：**28 项断言，全部通过**。

| 组 | 关键断言 | 实测 |
|---|---|---|
| 标准 | 两卡并排；网格左右内缩相等 | stacked=False；左内缩 38 / 右内缩 38 |
| 左手优先 | 竖排；右内缩 >> 左内缩；内容区右边缘收回；网格收窄；56px | stacked=True；右内缩 **322**；右边缘 1440→**1334**；网格 1110→**720**；min-height **56px** |
| 图形优先 | svg 本身放大 >1.5×；容器放大；箭头隐藏；卡片变高 | svg 43→**72px**（×1.7）；容器 118→148；箭头 `none`；226→355px |
| 字体 | 三档实际 computed 字体族互不相同 | `system-ui` / `Source Han Sans SC` / `Source Han Serif SC` |
| 图案 | calm 无图案；rich 有图案且够淡 | `none` / `radial-gradient(...)`，opacity 0.1 |
| 组合 | 四维度同时生效 | `pictogram + readable + rich + xlarge` ✓ |
| **窄屏 820px** | lefty 不再收窄；仍保留 56px；各档正常单列；图形优先图标克制 | 内容区 820=820；56px；stacked=True；svg 76px |

> **踩坑记录（三处断言写错，代码本身没问题）**：
> ① 用"屏幕左半边"当判据——`.page-content` 有 `max-width:1440px` 且居中，视口 1440 下左右各留 292px，卡片永远在中间，该断言**根本不成立**。
> ② 改用"比较 `pageContent.x`"——但 `.page-content` 的 `x` 恒为 **254**，那是 `.side-nav` 的宽度，任何规则都改不动。
> ③ 用"左内缩 < 8px"当"贴左"——但 `.page-content` 自带 `var(--sp-38)` 内边距，网格必然离左边界 38px，**这是设计的一部分**（正文不该顶到屏幕边）。
>
> 正确判据是**三个量一起看**：网格右侧内缩被拉到远大于左侧（38→322，证明靠左）、内容区右边缘从视口边收回（1440→1334，证明变窄）、网格自身宽度收窄（1110→720）。**教训：断言的必须是一个只有目标行为才能满足的量，否则会反复写错而不自知。**

### 14.6 窄屏回退

`@media (max-width: 900px)`（平板竖屏 / 手机）下：

- **撤销 lefty 的收窄**：窄屏本就没有横向余量，再收窄只会把内容挤成一条。还原为单列自然宽度。
- **保留 lefty 的 56px 触碰下限**：窄屏是拇指操作，触碰下限反而更重要，必须留着。
- 图形优先的图标占比**收敛**（76px）：窄屏视口小，图标一味放大会把文字挤没，失去"图标 + 文字"的互补关系。
